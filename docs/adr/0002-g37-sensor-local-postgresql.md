# Store G37 flows in sensor-local PostgreSQL

**Accepted topology and hard acceptance gates.** Provisioning and execution require separate authorization.

## Decision and rationale

For the first isolated monitoring pilot, run Zeek, one ingestion worker, and a dedicated PostgreSQL instance on the existing Ubuntu sensor VM. Bind PostgreSQL only to `127.0.0.1` inside the guest. Keep the existing VirtualBox Internal Network isolation. NAT, bridged, host-only, and external networking require explicit approval. Start with one vCPU and 2 GiB RAM and use guest-side verification. Keep the Windows application intact and defer dashboard integration until live ingestion, persistence, recovery, and sensor health are verified. [Approved pilot scope](0001-passive-single-site-zeek-pilot.md)

G36 verified ingestion from recorded replay. The current worker requires local PostgreSQL and commits flow inserts, file checkpoints, and health together. Co-location lets G37 exercise that transaction against native Zeek logs within the lab boundary. Offline transfer to Windows can support delayed review, but it would leave sensor-local persistence and recovery untested. The combined workload on the sensor VM remains unmeasured. The pilot will provide evidence for one bounded workload at one site. ## Declared workload and measurement windows

Use the traffic profile from the [G27 benign pilot fixture](../../examples/lab_benign_pilot.json). Each session has five completed transactions across three flows, two TCP and one UDP. Use fresh G37 session and capture IDs. Pin the fixture revision, Zeek version and settings, source ID, observation point, expected flow mapping, and measurement settings in a local run manifest before implementation.

- **Baseline and normal load.** On the same one-vCPU, 2 GiB sensor, run a 180-second Zeek-only baseline and a 180-second combined normal-load interval with Zeek, PostgreSQL, and the worker. Mark each start after its capture and observers are ready, then launch one fixture session in the first five seconds. Allow the full interval for native flow records to finalize and be observed. Each interval contains three fixed one-minute CPU windows.
- **Recovery.** After the combined normal-load interval, confirm all three rows are committed and record the drained checkpoint. Forcibly stop only the worker and confirm it exited. Keep PostgreSQL, Zeek, and packet recording running. Run one fixture session in the original active file, then close and rename that file to `conn.log.1` and open the new active file. Run one fixture session in the new file. Allow up to 180 seconds after each session starts for its three lines to become complete. Before restart, verify exactly three unread complete lines in each generation, six total, and record their keys, file identities, byte ranges, and total unread bytes. Keep the original `.1` inode in place and send no additional test traffic during timed recovery. Use the same source ID, active path, and settings when restarting the worker.

## Hard acceptance gates

- **Isolation.** Before each capture and at its end, record VirtualBox adapter state and the guest's interfaces, routes and forwarding state. Verify the PostgreSQL TCP listeners before the combined run, after the worker restarts, and at capture end. Monitor guest network changes while capturing. The existing Internal Network must remain the only attached network, with no external route or forwarding. During the combined run, PostgreSQL must listen only on `127.0.0.1` and test traffic must match the approved lab endpoints. Stop and record a failed pilot if the boundary is breached.
- **Capture and persistence.** Start packet recording before the first session and stop at the baseline endpoint or after combined recovery. Read the sensor interface `rx_dropped` counter at those boundaries and require no increase. Require zero in the independent recorder's final `packets dropped by kernel` count. Record native Zeek packet-source drops if exposed and require zero observed there as well. Report zero observed drops with the monitoring scope and available counters. Match completed client and service events to independent packet evidence and native Zeek JSON using session bounds and connection tuples. Match the combined run's nine native records to committed PostgreSQL rows by `(source, Zeek UID, first-packet timestamp)`. Require one persisted row per key, no missing or unexplained in-scope rows, and zero unexplained rejections. Keep unreviewed flow labels `unknown`.
- **Normal-load ingestion delay.** Use the guest's monotonic clock for both file and database observations. Track file identity and byte offset. Bracket each line's availability with the start of the last read that lacked its terminating newline and the completion of the first read that sees the entire line. Target 100 ms polling for file reads and fresh, independent PostgreSQL read transactions. Use the completion time of the first query that returns the matching committed row minus the start of the last incomplete file read as a conservative upper bound on the interval from complete line availability to successful persistence. Every normal-load row must meet the 5-second bound within that phase. Retain the observation timestamps and actual polling gaps. The Zeek event timestamp and the worker's precommit `ingested_at` are unsuitable for this gate.
- **Heartbeat and backlog recovery.** Start both timers on the guest monotonic clock when the supervisor issues the restart request, with the six complete rows already verified and PostgreSQL available. Read the checkpoint and matching rows in fresh PostgreSQL transactions. Within 15 seconds, require a committed `heartbeat_at` newer than the saved value and a successful processing timestamp that has advanced. Within 60 seconds, require all six expected recovery rows to be visible once, `backlog_bytes = 0`, and the checkpoint to reference the new file and reach its verified end. Compare the starting checkpoint and final counters to confirm exactly six new lines were processed. Retain `.1` through that committed handoff and verify its identity and SHA-256 digest afterward.
- **Duplicate prevention.** In a disposable sensor-mode source, persist a copy of one verified line, record its row count and duplicate counter, then append the same complete line again. Start the verification window when the second line's trailing newline is readable. Within 60 seconds, observe a committed checkpoint past the duplicate line, one additional counted duplicate, and the original row count. Preserve the original capture and native logs as read-only evidence.
- **Guest capacity.** Start sampling before each packet recording and finish at the baseline endpoint or when combined recovery ends, including an early stop. Sample CPU, memory, swap, and filesystem availability once per second. Use guest `/proc/stat` deltas across each one-minute combined normal-load window. Require less than 90% busy, using the first eight CPU counters for total time and subtracting idle and I/O wait for busy time. Record process CPU and resident memory to diagnose pressure. Require `/proc/meminfo` `MemAvailable` of at least 256 MiB at every sample, unchanged `/proc/vmstat` `pswpin` and `pswpout` counters, and no new kernel out-of-memory events during either interval. Require at least 1 GiB of space allocatable by an unprivileged process on each guest filesystem holding capture, log, or database data at every sample. Record log and database sizes at the start and end where applicable and report the baseline comparison. Recommend resizing only when a missed gate is attributable to measured resource pressure.

## Outcome and evidence

Record a failed pilot for any missed hard gate, including missing evidence needed to demonstrate a pass. Save the measured values, observer output, failure timestamps, worker and collector diagnostics, and the committed checkpoint state. Keep original captures and closed log generations with their SHA-256 digests in authorized local storage. Keep the declared thresholds fixed for this attempt and preserve its result if a later attempt uses a separately approved plan.

Report the result for this workload, guest allocation, and lab only. Production capacity, detection effectiveness, and deployment readiness require separate evidence.

## Path to multiple sensors

If centralized review is needed while the lab remains isolated, evaluate approved, integrity-verified export of closed batches. For an authorized connected deployment, evaluate authenticated delivery to a central ingestion endpoint using a versioned batch format and stable site, sensor, observation point, and source-record identities. Keep file checkpoints local to each sensor. Make central ingestion idempotent per source and acknowledge batches after durable commit, so sensors can retry while preserving observations from different vantage points. Choose transport, retention, and capacity limits when measured demand and deployment approvals justify them. Central integration remains future work.
